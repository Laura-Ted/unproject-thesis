# 2026-09-15 - ADR-0006: the campaign, and what changed in protocol v2

Protocol v2 says a change after a measurement needs a dated note. No final
measurement has been taken under it - the M4 run of this morning is a pilot
by its own account - but the text is amended today, and this is the note.

## What changed in `docs/experiments/protocol-v2.md`

| Section | Before | After |
|---|---|---|
| §2 Environment | one measuring machine, the M3 Pro; any other machine a pilot | a set of declared machines (`benchmarks/machines.toml`), each with an id every job records; one artifacts root per machine; the device chosen CUDA → Metal → CPU or insisted on, never a fallback; Linux conditions from `nvidia-smi`; the preflight |
| §3.2 | the transcode commands | plus: the four files are made once and carried, digests pinned |
| §4.1 | the person-count factor is not measured | not measured *by the matrix suite* |
| §4.2 (new) | - | the person-count suite, its four scenes, and the reading rule, fixed before collection |
| §8 | `artifacts/benchmark-v2/...` | `<root>/benchmark-v2/...` with `<root>` per machine; the preflight report beside the results |
| §10 (new) | - | the CPU-only point |
| §11 (new) | - | reading across machines: ratios per machine, no averaging |

Nothing in §5 (policy), §6 (metrics) or §7 (exclusion rules) changed. The
suite schema gained one optional field, `device`, whose default (`auto`)
leaves an existing suite's behaviour as it was; the suite hash of every
suite changes because the field is now part of the dump, which is right:
the campaign runs from this commit and no result from before it is a
campaign result.

## Why today

- The thesis asks about consumer hardware, and every number so far is from
  Apple Silicon. A Linux machine with a GeForce card is the point that
  makes the word mean what it says, and it was one `_select_device` away:
  the lockfile already carried CUDA 13 torch for Linux.
- The person-count factor was the one factor of ADR-0002 §8.3 never run.
  A one-repetition check this afternoon on three candidate clips showed
  about +11 ms per detected person on the M4; enough to pre-register a
  suite, not enough to quote.
- Two machines were about to write under the same `artifacts/benchmark-v2/`
  and be averaged by a summary that could not tell them apart.

## What was verified before writing this

- The full gate list is green on this tree (ruff, format, mypy strict,
  pytest in both invocations, validate-config, `uv lock --check`).
- On the M4: `benchmark-preflight` on the matrix suite finds every input
  by digest and reports `mps: Apple M4, 4 torch thread(s)`; a real job on
  the fixture clip runs on Metal (0.65 s/frame median) and, held to the CPU
  with `UNPROJECT_DEVICE=cpu`, on the CPU (1.27 s/frame); asked for CUDA it
  refuses with the message a Linux operator needs.
- The CUDA path has not run yet: no NVIDIA machine was available today. The
  first thing the rented instance does is the preflight, and the first
  job's result names the device, the card, CUDA and the driver.

## What is deliberately not done here

- No result is produced. The campaign starts when the author's `walkers`
  clip exists, because adding it to the people suite changes the suite
  hash and everything must run from one commit.
- The `crowd` clip and the v1 benchmark are untouched; they remain the
  pilot.
- MuPoTS-3D is not re-run anywhere: accuracy does not depend on the
  machine.
